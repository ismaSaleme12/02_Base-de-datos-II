# Verificación de roles — Parte A (ejecución real 2026-10-05)
## Base `practica_bd2_tp` (restaurada de Food_Store_Copia) · PostgreSQL 18.6 · usuario postgres

Comandos:
```sql
\du
SELECT rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole FROM pg_roles
 WHERE rolname IN ('rol_app_lectura','rol_app_escritura','rol_soporte','rol_reportes','app_web','admin_datos') ORDER BY 1;
SELECT r.rolname AS login, m.rolname AS grupo FROM pg_auth_members am
 JOIN pg_roles r ON r.oid=am.member JOIN pg_roles m ON m.oid=am.roleid
 WHERE r.rolname IN ('app_web','admin_datos') ORDER BY 1,2;
SELECT grantee, table_name, privilege_type FROM information_schema.role_table_grants
 WHERE grantee IN ('rol_app_lectura','rol_app_escritura','rol_soporte','rol_reportes','app_web','admin_datos')
 ORDER BY 1,2,3;
SELECT grantee, table_name, column_name, privilege_type FROM information_schema.role_column_grants
 WHERE grantee IN ('rol_app_lectura','rol_reportes','rol_soporte') ORDER BY 1,2,3;
```

### Criterios CA (SET ROLE real)

- `SET ROLE app_web; SELECT * FROM cliente LIMIT 1;` → `ERROR: permiso denegado a la tabla cliente` ✅
- `SET ROLE app_web; SELECT * FROM v_productos_vigentes_con_categoria LIMIT 1;` → 1 fila ✅
- `SET ROLE app_web; GRANT admin_datos TO app_web;` → `ERROR: se ha denegado el permiso para otorgar el rol` ✅
- `has_column_privilege('rol_soporte','usuario','password_hash','SELECT')` → `f` ✅

## Hallazgo y corrección (constancia)

La primera versión de `roles.sql` hacía `GRANT SELECT ON usuario TO rol_soporte`
+ `REVOKE SELECT (password_hash)`. La verificación real mostró que
`password_hash` seguía accesible: en PostgreSQL el `REVOKE` por columna NO
recorta un `GRANT` a nivel tabla. Se corrigió a `REVOKE ALL ON usuario` +
`GRANT SELECT (id,nombre,email,rol,fecha_alta,activo)` (sin `password_hash`),
y la re-ejecución confirmó `c_hash=f, c_email=t`. Este es el caso testigo de
validación humana de la Parte A.
